Use this guide if you already have a website configured with
[Welcomments](https://welcomments.io/), its website ID and a working integration
that delivers comment files to this repository. Configure that service-side
integration using the provider's instructions before testing new submissions.

## Review the integration files

Review any pull request generated by Welcomments before merging it. Retain the
customized `_includes/welcomments/` templates supplied by
<span class="chulapa">Chulapa</span>, rather than replacing them with generic
provider templates. Review any local copies left by another theme: local files
override the installed theme's files.
{: .alert .alert-warning .p-3 .mx-2 .mb-3}

Keep the provider's comment data and repository integration. The theme reads
comment data from `_data/welcomments/`; the website ID alone does not deliver
that data or configure the external service.

## Select Welcomments

In `_config.yml`, edit the existing `comments` section, or add it once if absent.
Replace the example website ID and preserve unrelated settings:

```yaml
comments:
  provider: welcomments
  website_id: "YOUR_WELCOMMENTS_WEBSITE_ID"
```

## Check the form URL on a project site

In v2.2.0, the theme form uses the full published
article URL, including `baseurl`. The v2.1.0 form omits that path: for a site
such as `https://ana.github.io/my-blog`, its submitted URL can point outside
`/my-blog`. Use the local correction below on v2.1.0 and review existing overrides
when upgrading; local forms override the fixed theme.
{: .alert .alert-warning .p-3 .mx-2 .mb-3}

For a v2.1.0 site with `baseurl`, copy the theme's
[customized form](https://github.com/dieghernan/chulapa/blob/main/_includes/welcomments/comment_form.html)
to `_includes/welcomments/comment_form.html` in your repository. Use the file
from your installed theme version; the linked `main` file is the development
version. Preserve the rest of that file; replace only the hidden `permalink`
input with:

{% raw %}
```html
<input type="hidden" name="permalink" id="permalink" value="{{ page.url | absolute_url | escape }}">
```
{% endraw %}

When you publish the post below, inspect its hidden `permalink` value in your browser's
developer tools. It must match the full article address, including the project
path. Keep this local override under review when upgrading the theme.

## Enable one post

Open an existing post using `layout: default`. Add or update this value between
its existing `---` lines, preserving the title, date, layout and other settings:

```yaml
show_comments: true
```

Selecting a provider alone does not enable comments on the page. Save all changes
on the publishing branch, wait for **Actions** to succeed and open the article
on your public website.

## Verify the form and saved comment

Check the form below the article. If appropriate, submit a test comment, verify
that the service delivers its data to your repository, then check that a
successful site rebuild displays it. A temporary browser placeholder is not
proof that the comment has reached the published static site.

If the form is missing, check the website ID, `show_comments`, layout and local
template overrides. If a submitted comment never appears after a rebuild, check
the provider's repository integration and delivered data, and confirm that the
post's slug still matches its existing comment data. Renaming a post can change
that match; switching providers does not transfer old comments automatically.

For more posts, set `show_comments: true` individually or merge it into an
appropriate existing [front matter default](./04-layouts#a-note-on-defaults).
Other providers and exact fields are in [the comments reference](./02-config#comments).
